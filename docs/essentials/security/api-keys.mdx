API keys let you reach QuivaWorks programmatically for automation, integrations and custom applications.

## Creating an API Key

<Steps>
  <Step title="Open the API keys tab">
    Open **Settings** from your user menu, then the **API keys** tab
  </Step>

  <Step title="Add a new key">
    Click **Add**. A "Create API Key" dialog opens.
  </Step>

  <Step title="Name your key">
    Enter a descriptive name — "Production integration", "CI pipeline", "Monitoring script"
  </Step>

  <Step title="Save the key">
    The key is displayed once, with **Copy** and **Download Credentials** buttons. Take it now.
  </Step>
</Steps>

<Warning>
**The key is only shown once.** Once you close the dialog it cannot be displayed again. Copy it into a password manager or secret store before you close it.
</Warning>

<Note>
The **API keys** tab is not available to users with the client role.
</Note>

## Key Types

### Scope

Every key carries a scope. The Settings screen creates **user-scoped** keys; the account scope is available when a key is created through the API.

<CardGroup cols={2}>
  <Card title="User scope" icon="user">
    The default. The key is tied to the user who created it and carries that user's role and permissions.
  </Card>

  <Card title="Account scope" icon="building">
    Only root and admin users may create one, and the scope is re-checked whenever the key is used.
  </Card>
</CardGroup>

<Warning>
An account-scoped key has a far larger blast radius than a user-scoped one. Create one only when a user-scoped key genuinely cannot do the job, and hold it to the same handling standard as the root account's password.
</Warning>

### Restricted keys

Supplying a list of allowed endpoints when the key is created produces a **restricted** key. Each entry pins the key to a particular HTTP method and path, optionally on a specific gateway. Anything outside that list is refused.

Restricted keys carry the `msr-` prefix instead of `ms-`, and are the right choice whenever a key only ever needs to make a small, known set of calls — a webhook receiver, a scheduled export, a single integration.

<Info>
Restricted keys do not come with a downloadable credentials file. Use the key value itself.
</Info>

### Key prefixes

| Prefix | Meaning |
|---|---|
| `ms-` | A standard key |
| `msr-` | A restricted key, limited to specific endpoints |

The prefix uses a hyphen, not an underscore.

## Expiry

Keys expire after **90 days** by default. When a key is created through the API the lifetime is configurable, and a negative value produces a key that never expires.

You get two emails around expiry:

- A **warning** 7 days before the key expires, provided the key's lifetime was at least 7 days
- A **notification when it expires** — the key is deleted at that point and stops working

<Warning>
A key that never expires never gets rotated by the platform on your behalf. If you create one, own the rotation schedule yourself.
</Warning>

## Managing API Keys

### Viewing your keys

The **API keys** tab lists your keys with these columns:

| Column | Shows |
|---|---|
| **Name** | The name you gave the key |
| **Account** | The account the key belongs to |
| **Last 4 Characters** | The final four characters, for identifying a key you hold |
| **Created** | When the key was issued |
| **Expires** | When the key stops working |

<Info>
There is no "last used" column, and QuivaWorks does not currently provide audit logs for API usage. If you need to know when and how a key is being used, log that in the application that holds the key.
</Info>

### Downloading credentials

**Download Credentials** in the tab's menu produces a credentials file for a key you already hold — you paste the key value in to retrieve it. It is available for standard keys, not restricted ones.

<Warning>
A downloaded credentials file authenticates as the key. Store it the same way you'd store the key itself, and delete it from your Downloads folder once it's in your secret store.
</Warning>

### Deleting a key

Use **Delete Key** in the tab's menu, or open a key from the list and delete it from there.

<Note>
Deletion takes effect immediately. Anything using that key stops working at once, so deploy a replacement first.
</Note>

## Security Best Practices

<Warning>
**Treat API keys like passwords.** Never share them or expose them publicly.
</Warning>

### Storage and handling

<AccordionGroup>
  <Accordion title="Use environment variables" icon="check">
    **Do this:**
    ```bash
    export QUIVA_API_KEY="ms-your-key-here"
    ```

    **Never do this:**
    ```javascript
    // Don't hardcode keys in your source
    const apiKey = "ms-abcdef0123456789"; // BAD
    ```
  </Accordion>

  <Accordion title="Use a secret manager" icon="vault">
    Store keys in a purpose-built secret store:
    - AWS Secrets Manager
    - HashiCorp Vault
    - Azure Key Vault
    - Google Secret Manager
    - A team password manager

    These give you encrypted storage, access control, and a record of who read what.
  </Accordion>

  <Accordion title="Never commit to version control" icon="code-branch">
    Add these patterns to your `.gitignore`:
    ```
    .env
    .env.local
    .env.*.local
    *.creds
    ```

    Even a private repository is the wrong place for a key — forks, access changes, CI logs and backups all leak it.
  </Accordion>

  <Accordion title="Don't share keys between people" icon="users-slash">
    **Never send a key by:**
    - Email
    - Chat message
    - A shared document or spreadsheet

    **Instead:**
    - Issue a separate key per person or per system
    - Distribute through your secret manager
    - Use a restricted key when the consumer only needs a few endpoints
  </Accordion>
</AccordionGroup>

### Rotation

<Steps>
  <Step title="Create the replacement">
    Issue a new key ahead of the old one's expiry date — the 7-day warning email is a useful trigger
  </Step>

  <Step title="Deploy it">
    Update environment variables, secret manager entries and CI configuration
  </Step>

  <Step title="Verify">
    Confirm every integration works on the new key before going further
  </Step>

  <Step title="Delete the old key">
    Only once nothing is still using it
  </Step>
</Steps>

### Organising multiple keys

<CardGroup cols={2}>
  <Card title="One key per environment" icon="layer-group">
    Separate keys for production, staging, development, CI and each third-party integration. A leak then has a bounded blast radius.
  </Card>

  <Card title="Descriptive names" icon="tag">
    The name and the last four characters are all you have to identify a key later:
    - "Production — web app"
    - "CI — main pipeline"
    - "Monitoring integration"
  </Card>
</CardGroup>

## If a Key is Compromised

<Warning>
Act immediately if you suspect a key has been exposed.
</Warning>

<Steps>
  <Step title="Delete it">
    **Settings → API keys → Delete Key**. This revokes it instantly.
  </Step>

  <Step title="Issue a replacement">
    Create a new key — and consider making the replacement a restricted key
  </Step>

  <Step title="Update everything using it">
    Deploy the new key to every affected service
  </Step>

  <Step title="Review your own logs">
    QuivaWorks has no API audit log, so your application's logs are the only record of what the key did. Check them for calls you can't account for.
  </Step>

  <Step title="Work through the wider response">
    If the exposure may extend beyond the key itself, follow the [incident response steps](/essentials/security/incident-response)
  </Step>
</Steps>

**Common ways keys get exposed:**
- Committed to a public repository
- Written to application logs in plain text
- Pasted into a chat or an email
- Included in an error message or stack trace
- Left in an unencrypted configuration file or a Downloads folder

## Using API Keys

Send the key as a bearer token in the `Authorization` header:

```bash
curl -H "Authorization: Bearer $QUIVA_API_KEY" \
     -H "Content-Type: application/json" \
     "$YOUR_ENDPOINT"
```

<Info>
HTTP paths are defined per account by your own gateway mappings, so there is no single shared base URL to publish here. Use the endpoint your account exposes.
</Info>

<Tabs>
  <Tab title="Node.js">
    ```javascript
    const apiKey = process.env.QUIVA_API_KEY;

    const response = await fetch(process.env.QUIVA_ENDPOINT, {
      headers: {
        'Authorization': `Bearer ${apiKey}`,
        'Content-Type': 'application/json'
      }
    });
    ```
  </Tab>

  <Tab title="Python">
    ```python
    import os
    import requests

    api_key = os.environ['QUIVA_API_KEY']

    headers = {
        'Authorization': f'Bearer {api_key}',
        'Content-Type': 'application/json'
    }

    response = requests.get(os.environ['QUIVA_ENDPOINT'], headers=headers)
    ```
  </Tab>

  <Tab title="cURL">
    ```bash
    curl -H "Authorization: Bearer $QUIVA_API_KEY" \
         -H "Content-Type: application/json" \
         "$QUIVA_ENDPOINT"
    ```
  </Tab>
</Tabs>

### Error responses

Errors come back in this shape:

```json
{
  "status_code": 401,
  "body": {
    "error": "..."
  }
}
```

<AccordionGroup>
  <Accordion title="401 Unauthorized" icon="circle-xmark">
    **Common causes:**
    - The key doesn't exist or was deleted
    - The key expired and was removed automatically
    - The key was copied incorrectly — truncated, or with whitespace
    - The `Authorization` header isn't formatted as `Bearer <key>`

    **Fix:** check the key still appears in **Settings → API keys**, then reissue it if not.
  </Accordion>

  <Accordion title="403 Forbidden" icon="ban">
    **Common causes:**
    - The owning user's role doesn't permit the operation
    - The resource belongs to a different account
    - The key is restricted and this method or path isn't in its allowed list

    **Fix:** check the role of the user who owns the key, and — for an `msr-` key — whether the call is one the key was pinned to.
  </Accordion>

  <Accordion title="429 Too Many Requests" icon="gauge-high">
    A rate-limited response has a **plain-text** body, not JSON, and carries a **`Retry-After`** header telling you how long to wait.

    **Fix:** read `Retry-After` and back off for at least that long. Implement exponential backoff for repeats.
  </Accordion>
</AccordionGroup>

## Checklist

### Before creating a key

- [ ] Decide whether user scope is sufficient — it usually is
- [ ] Decide whether it can be a restricted key pinned to specific endpoints
- [ ] Identify which user should own it, since the key inherits their permissions
- [ ] Choose a descriptive name
- [ ] Have the secret store ready before you click Add

### On creation

- [ ] Copy the key straight into your secret store — it is shown only once
- [ ] Record where the key will be used
- [ ] Note the expiry date

### In use

- [ ] Read the key from an environment variable or secret manager, never a literal
- [ ] Log API errors, but never log the key
- [ ] Keep separate keys per environment

### Ongoing

- [ ] Review your key list periodically and delete anything unused
- [ ] Rotate ahead of expiry — the 7-day warning email is your prompt
- [ ] Re-check any key that never expires

## Troubleshooting

<AccordionGroup>
  <Accordion title="Key doesn't work right after creation">
    - Confirm the key was copied whole, with no leading or trailing whitespace
    - Check the header format: `Authorization: Bearer <key>`
    - Confirm the endpoint exists in your account's gateway mappings
    - Confirm the owning user's role permits the operation
  </Accordion>

  <Accordion title="Key stopped working suddenly">
    - It may have reached its expiry date and been deleted automatically
    - Someone may have deleted it — check whether it still appears in the list
    - The owning user's role may have changed, or the user may have been suspended or deleted
  </Accordion>

  <Accordion title="Calls refused on a restricted key">
    An `msr-` key only permits the method and path combinations it was pinned to at creation. There is no way to widen an existing restricted key — issue a new one with the endpoints you need.
  </Accordion>

  <Accordion title="Key accidentally exposed">
    1. Delete it immediately
    2. Issue a replacement
    3. Update every application using it
    4. Review your own application logs for calls you can't account for
  </Accordion>
</AccordionGroup>
