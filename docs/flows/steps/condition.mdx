# Condition Step

A Condition step is the only thing in a flow that chooses a branch. Its payload is a ladder of rule cells; the first cell whose condition is true wins, and that cell's **outcome** names the step IDs to run next.

<Warning>
**The outcome is the routing, not the arrows.** An edge drawn from a Condition to a step that no outcome names is decoration — it is never followed. An outcome naming a step that is not in the flow fails the run with `next step not found`.
</Warning>

---

## The payload

The payload is a JSON **array of rule cells**, and nothing wraps it:

```json
[
  { "condition": { "operator": ">=", "input": ["$.SCORE.data.value", 80] }, "outcome": "NOTIFY_OWNER" },
  { "condition": { "operator": ">=", "input": ["$.SCORE.data.value", 50] }, "outcome": "REVIEW" },
  { "outcome": "ARCHIVE" }
]
```

Cells are tried top to bottom. A cell with **no** `condition` always matches, so a final bare `{"outcome": …}` is the `else`. If no cell matches, the step fails with `failed to determine next steps`.

<ParamField path="condition.operator" type="string" required>
The comparison to run. Must be one of the engine's operator names — see [the operator reference](/advanced/rules/operations-reference).
</ParamField>

<ParamField path="condition.input" type="array" required>
The operands. `input[0]` is the value being tested, `input[1]` is what it is tested against. An operand may itself be another `{operator, input}` object, which is how `and` / `or` / `not` are built.
</ParamField>

<ParamField path="outcome" type="string | string[]" required>
The step ID to run next, or an array of step IDs. **Several IDs start at the same time.**
</ParamField>

<Note>
`outcomeMessage` is accepted but has no effect on a Condition step — the runner reads only the outcome.
</Note>

---

## Where the values come from

**A Condition step has no facts.** The rules engine is called with an empty fact set, so `@fact:` references and `{"operator": "fact", …}` resolve to nothing and the cell silently never matches.

Values come in through JSONPath instead. The whole payload is resolved before the engine sees it, so a `$.` string anywhere in `input` is replaced by the value it selects:

```json
{ "operator": ">=", "input": ["$.SCORE.data.value", 80] }
```

With `$.SCORE.data.value` equal to `92`, the engine receives `{"operator": ">=", "input": [92, 80]}` and the cell matches.

<Warning>
**A path that matches nothing resolves to an empty array, not `null`.** `"$.SCORE.data.missing"` becomes `[]`, and `[] >= 80` is false — so the branch quietly falls through to the next cell rather than erroring. Test the path in the previous step's output before relying on it.
</Warning>

## Ending a run

Two reserved outcomes are not step IDs:

| Outcome | Effect |
|---|---|
| `RESOLVE_SUCCESS` | Ends the run, marked successful |
| `RESOLVE_ERROR` | Ends the run with `flow terminated with error` |

```json
[
  { "condition": { "operator": "notEmpty", "input": ["$.GET_ITEMS.data"] }, "outcome": "PROCESS_ITEMS" },
  { "outcome": "RESOLVE_SUCCESS" }
]
```

## Worked examples

Each of these was run through the rules engine the step uses; the outcome shown is what it returned.

### Fan out to two steps

```json
[
  { "condition": { "operator": ">=", "input": ["$.SCORE.data.value", 80] },
    "outcome": ["NOTIFY_OWNER", "WRITE_LOG"] },
  { "outcome": "ARCHIVE" }
]
```

With the score at 92 the outcome is `["NOTIFY_OWNER", "WRITE_LOG"]`, and both steps start together.

### Combine two tests

`and`, `or` and `not` take nested `{operator, input}` objects as their operands:

```json
[
  { "condition": { "operator": "or", "input": [
      { "operator": "=", "input": ["$.CLASSIFY.result", "urgent"] },
      { "operator": ">", "input": ["$.CLASSIFY.wait_days", 5] }
    ] },
    "outcome": "ESCALATE" },
  { "outcome": "RESOLVE_SUCCESS" }
]
```

### Match on text

```json
[
  { "condition": { "operator": "stringContains", "input": ["$.trigger.subject", "refund"] },
    "outcome": "BILLING" },
  { "outcome": "GENERAL" }
]
```

### Range test

`between` takes the bounds as a **nested pair**, not as two more operands:

```json
{ "operator": "between", "input": ["$.ORDER.data.total", [100, 500]] }
```

Written flat as `["$.ORDER.data.total", 100, 500]` it returns `false` for every value.

## The failure that gives no error

<Warning>
**An operator the engine does not have produces no error and no value.** The engine records an internal warning that is never returned, the cell resolves to nothing, and the ladder carries on to the next cell — so the branch simply never fires and nothing in the run log says why.

Two names in the editor's own operator dropdown are affected: **`boolean`** and **`string-contains`** are not implemented. Use `stringContain` / `stringContains` for the latter; there is no `boolean` operator.

The same silence covers operator names people reasonably expect and the engine does not have, among them `includes`, `startsWith`, `endsWith`, `toLower`, `trim`, `size` and `isEmpty`.
</Warning>

If a Condition step **errors** rather than mis-routing, it is almost always one of two things:

| Error | Cause |
|---|---|
| `failed to determine next steps` | No cell matched, the payload is empty, or the only cell uses an operator that does not exist. A newly inserted cell starts with an empty operator and hits this. |
| `value has to be a string or an array of strings` | The winning cell's `outcome` is not a step ID — an object or a number, usually from an `if`/`then`/`else` shape that the engine passed through as a literal. |

## The Conditions editor

The Condition step has two views, switched at the top of the payload pane:

| View | Use |
|---|---|
| **Code Editor** | The rule-cell array as raw JSON |
| **Conditions** | One collapsible card per cell, labelled IF / ELSE IF / ELSE |

In the Conditions view, each cell has an **Input** field (which takes a `$.` path), an **Operator** dropdown, a **Value** editor, and an **Outcome** multi-select listing the steps this condition connects to. Both views edit the same array — switching between them loses nothing.

---

## The step's own result

A Condition step **stores nothing**. `$.my_condition` holds no value, because the runner hands off to the chosen branches instead of recording a result. If a later step needs the decision itself, compute it in an [Eval](/flows/steps/eval) or [Rules](/flows/steps/rules) step and branch on that step's output.

<Note>
Editing a flow changes its **draft**. **Publish** to make a routing change take effect.
</Note>
