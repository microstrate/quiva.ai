# Assistant Step

An Assistant step runs one of your saved assistants and stores its reply for the rest of the flow.

<Warning>
**The step points at a saved assistant; it does not define one.** The step holds a reference — `subject` — to an assistant that exists in your account. Everything the assistant *is* — its instructions, model, knowledge and integrations — is stored on the assistant itself and is shared by every flow that uses it. Editing those settings from inside a flow edits the assistant, so the change lands on every other flow using it too.

The step's own settings are only the handful listed below.
</Warning>

---

## Choosing the assistant

The **General** tab has a **Select Assistant** dropdown listing the assistants in your account, and an **Edit Assistant Details** button that opens the assistant's own configuration.

You can also drag an assistant onto the canvas from the flow editor's **Assistant** control, which offers **Select Assistant** (use an existing one) and **Create Assistant** (make a new one and reference it).

---

## What the step itself holds

<ParamField path="prompt" type="string">
What to ask. **Leave it empty and the run's trigger is used as the prompt** — which is what you want for an assistant wired straight to the trigger. When the assistant sits after other steps, map the prompt in:

```json
{ "prompt": "Summarise this ticket for the on-call team:\n|$.GET_TICKET.data.body" }
```
</ParamField>

<ParamField path="global_instructions" type="boolean" default="false">
Include the account's global instructions in this invocation.
</ParamField>

<ParamField path="global_knowledge" type="boolean" default="false">
Include the account's global knowledge in this invocation.
</ParamField>

<ParamField path="escalate_user_ids" type="string[]">
**Escalate To** — the users who can be assigned as the admin when this assistant escalates a conversation.
</ParamField>

The remaining tabs — **Provider**, **Instructions**, **Knowledge**, **Integrations**, **Context** — edit the *assistant*, not the step. They are documented under [Assistants](/assistants/overview).

<Note>
Two settings that look like step settings are not honoured here. The step always waits for the assistant, for up to five minutes; there is no run-in-background mode on an assistant step, and the **Await** toggle on the assistant does not change that.
</Note>

---

## What the step returns

The assistant's response object, stored flat under the step ID. The fields worth knowing:

| Field | Contents |
|---|---|
| `result` | **The assistant's answer.** A string, or an object if the assistant has an output schema. |
| `success` | Whether the invocation succeeded |
| `thinking` | The model's reasoning, when the provider returns it |
| `session_id` | The conversation this turn belongs to |
| `provider`, `model` | Which model actually answered |
| `input_tokens`, `output_tokens`, `total_tokens`, `cost` | Usage for this turn |
| `duration_ms` | How long it took |
| `warnings` | Non-fatal problems, such as a knowledge source that failed to load |

```
$.CLASSIFY.result
$.CLASSIFY.model
```

<Warning>
The answer is at `$.STEP_ID.result`, not `$.STEP_ID.response` and not `$.STEP_ID` on its own.
</Warning>

If the assistant has an output schema, `result` is an object and you can read into it directly — `$.CLASSIFY.result.category`. Bear in mind that an output schema is a set of field descriptions given to the model as guidance; it is not validated, so a field can come back missing.

## Sessions and context

If the run was started with a session — a chat-driven flow, for instance — every assistant step in it invokes into that same session, so a second assistant sees what the first one said. **A run with no session gives each assistant step a session of its own**, and they share no history.

Context variables passed in on the run request are forwarded to the assistant automatically.

<Warning>
Do not set `context` in the step's own payload. The run's context variables are what reach the assistant, and a step that carries its own `context` object in a run that also has context variables fails the run.
</Warning>

---

## When an assistant pauses the run

An assistant can stop the flow rather than answer it, and the run parks the same way a [Checkpoint](/flows/steps/human-in-the-loop) does:

| Response | Run status | Meaning |
|---|---|---|
| `complete: false` | **in progress** | The assistant needs more from the person before it can finish |
| `escalate: true` | **paused** | The assistant has handed the conversation to a human |

In both cases the step stores no result and nothing downstream runs. The run is picked up again from the Monitoring page, or by continuing the conversation in chat — the run detail panel offers a **Join to Chat** button for a paused assistant session.

---

## What an assistant step cannot do

<Warning>
Several controls people look for on this step live somewhere else, or nowhere:

- **No output validation or retry loop.** An output schema shapes the prompt; nothing checks the reply against it or asks again.
- **No boundaries or guardrail fields.** Constraints go in the assistant's instructions.
- **No per-step memory toggle.** Memory is a property of the assistant and its session.
- **No `topP`, `frequencyPenalty`, `presencePenalty` or stop sequences.** The assistant's Provider tab offers **Temperature**, **Max Turns** and **Max Output Tokens**, and that is the whole set.
</Warning>

<Note>
Editing a flow changes its **draft**, but editing an assistant from inside a flow saves the **assistant** immediately — that change is live for every flow and chat using it, published or not.
</Note>
