# Flow Steps

A flow is a graph of steps. A trigger starts a run; the runner then works through the graph, resolving each step's payload against the data collected so far and storing the step's result under its step ID.

<Warning>
**Steps do not run in sequence.** The runner is a concurrent graph executor. Every step with no incoming edge starts at once, and a step starts as soon as all of its predecessors have finished — so independent branches run in parallel. This is also why one failure stops everything: the first error cancels the run, and any step still in flight is abandoned.
</Warning>

---

## The step types

| Step | What it does |
|---|---|
| [Assistant](/flows/steps/agents) | Runs a saved assistant and stores its reply |
| [Condition](/flows/steps/condition) | Decides which step or steps run next |
| [Map](/flows/steps/map) | Reshapes data into a new object using JSONPath |
| [Eval](/flows/steps/eval) | Runs a small piece of JavaScript |
| [Rules](/flows/steps/rules) | Derives values from a rule set |
| [HTTP Request](/flows/steps/http-request) | Calls an external API |
| [Integration](/flows/steps/api-integrations) | Calls one action on a connected integration |
| [Function](/flows/steps/functions) | Runs one of the platform's built-in functions |
| [Nested flow](/flows/steps/nested-flows) | Runs another flow |
| [Checkpoint](/flows/steps/human-in-the-loop) | Pauses the run for a person to action |
| [Delay](/flows/steps/delay) | Waits a fixed number of milliseconds |

Several more node types exist and are dispatched by the runner but have no page of their own yet: **Error** (ends the run with a status code and message), **Schedule** (schedules another flow to run later), **Task**, **Verify Challenge**, **Quiva Endpoint** and **Static**.

Triggers are documented separately — see [Triggers](/flows/triggers/overview).

## What a step can read

Before a step runs, its payload is resolved: every string beginning with `$.` is replaced by the value that JSONPath selects. The data it selects from has these top-level keys and nothing else:

| Key | Contents |
|---|---|
| `trigger` | The payload that started the run |
| `static` | The flow's Static data, itself resolved at the start of the run |
| `context` | Context variables passed in on the run request |
| `env` | `auth_token`, `run_id` and `headers` for this run |
| *step ID* | The result of a step that has already finished |

```
$.trigger.customer.email
$.GET_ORDER.data.total
$.env.run_id
```

<Warning>
There is no `${…}` syntax, no `secrets` key, and no filter or pipe grammar. `|` inside a string is a **join**: `"Order |$.GET_ORDER.data.id| received"` builds one string out of literal text and resolved values. That is the whole of it.
</Warning>

A result is stored flat under the step's ID. There is no `.output` or `.result` wrapper — although an assistant's own reply happens to live at `$.STEP_ID.result`, because that is a field of the response it returns.

## What runs next

**A Condition step's outcome names the step IDs to run.** Everything else follows from that:

- An outcome may name one step, or several — several start at the same time.
- Two reserved outcomes end the run: `RESOLVE_SUCCESS` finishes it successfully, `RESOLVE_ERROR` fails it.
- An outcome naming a step that is not in the flow fails the run with `next step not found`.
- **An edge drawn from a Condition to a step that no outcome names is decoration.** Edges are used only to work out when a step's predecessors are all done; a branch the condition did not choose is skipped.

For every other step type, the edges are the routing: when a step finishes, each step it points at runs once all of *its* predecessors have finished.

<Note>
A Condition step stores no result. `$.my_condition` holds nothing, because the runner returns before writing the result for that node type.
</Note>

## When a step fails

There is no per-step error branch. The first step to error records the failure, marks the run `error` and cancels it — no downstream step runs, and the failed step leaves no result for anything to inspect.

Two settings soften this, both under **Advanced Settings** on the steps that support them:

| Setting | Effect |
|---|---|
| `attempts` | Total attempts, not retries. Capped at 5. |
| `backoff_ms` | A **constant** wait between attempts. There is no exponential backoff. |
| `ignore_response_codes` | Response codes that must not trigger a retry. It does **not** stop them failing the step. |
| `timeout` | Per-step timeout in milliseconds |
| `flat_map` | Flattens the step's result to dotted keys before storing it |

To end a run deliberately, use a Condition outcome of `RESOLVE_ERROR`, or an **Error** step, which sets a status code and message.

---

## Step IDs

A step ID must start with a letter or underscore and may then contain letters, digits, underscores and colons. IDs must be unique within a flow, and four are reserved and cannot be used: `trigger`, `static`, `RESOLVE_SUCCESS` and `RESOLVE_ERROR`.

Every step must have a payload, even an empty one. Function and nested-flow steps must additionally name a subject.

---

## Draft and published

Editing a flow changes its **draft**. Save keeps your work; **Publish** is what makes the change take effect for live runs. Testing in the editor runs the draft, so a flow that behaves correctly under test can still be running its old published version in production until you publish.
