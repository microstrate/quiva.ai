# Building Reliable Flows

One failure ends a whole run. That single fact drives most of what follows: there is no per-step error branch, no dead-letter queue and no automatic replay. A flow that matters has to be designed so that ending halfway through is survivable.

This page covers what the runner actually does. For the step types themselves see [Steps](/flows/steps/overview); for what can start a run see [Triggers](/flows/triggers/overview).

---

## What a failure does

The first step to error wins, and everything after it is a consequence:

1. The error is recorded against the run, and the run's status becomes `error`.
2. The run is cancelled. No further step starts.
3. Steps already in flight are abandoned — they are not waited for and their results are discarded.
4. The results of steps that *had* finished are kept and returned with the failure.
5. The failed step itself stores nothing, so there is no result for a later step to inspect.

Because branches run in parallel, "steps that had finished" can include work on a branch unrelated to the one that failed. A run that dies at step 7 may already have written to storage at step 3.

<Warning>
**Design writes to be safe to repeat, and put them as late as you can.** The runner will not undo a write made before the failure, and rerunning the flow makes it a second time.
</Warning>

## Recovering a run

Open **Monitoring**, select the run, and three controls appear depending on its status:

| Control | Available when | Does |
|---|---|---|
| **Retry** | status is `error` | Resumes **from the step that errored**, with the original trigger and the flow configuration as it was when the error happened. Steps that already succeeded are not repeated. |
| **Continue** | status is `paused` | Resumes a [Checkpoint](/flows/steps/human-in-the-loop) from where it paused. You can supply a message, which becomes the paused step's result. |
| **Rerun** | status is `error` or `paused` | Opens the trigger for editing and runs again. |

**Retry** is possible because the failure is captured with everything needed to carry on: the results of every completed step, and the remainder of the graph from the failed step onward. It is the right control after a transient failure — an API that was down, a timeout, a bad credential you have since fixed.

<Note>
If you have **changed the flow** since it failed, do not rely on these controls to pick the change up. Retry deliberately replays the configuration version the run started with. Publish the fix and trigger the flow again.
</Note>

## Retries

Retries are configured per step, under **Advanced Settings**, and are **off by default**.

<ParamField path="attempts" type="integer">
Total attempts, not additional ones. `1` or `0` means no retry. Values above `5` are capped at `5`.
</ParamField>

<ParamField path="backoff_ms" type="integer">
Milliseconds to wait between attempts. It is a **constant** wait — there is no exponential backoff and no jitter.
</ParamField>

<ParamField path="ignore_response_codes" type="array">
Response codes that must not trigger a retry.
</ParamField>

<ParamField path="timeout" type="integer">
Per-step timeout in milliseconds.
</ParamField>

Only four step types retry: **Function**, **HTTP Request**, **Integration** and **nested flow**. Setting `attempts` on a Map, Eval, Rules or Condition step does nothing — those either work or they do not.

<Warning>
**"Ignore Response Codes" does not ignore the error.** A code in that list is logged, the retry is skipped, and the step still fails the run. There is no setting that lets a flow continue past a 4xx or 5xx from an HTTP Request step. If a non-2xx response is a normal outcome for your integration, call it through a Function step and branch on the body instead.
</Warning>

A retry re-runs the step from the beginning, including its side effect. A step that publishes a message, writes a key or posts to an API will do it again.

<Tip>
Make repeated work harmless rather than trying to prevent it:

- Write under a **deterministic key** — the order ID, not a timestamp — so a repeat overwrites rather than duplicating.
- Read before you write when a duplicate would be visible to a person.
- Keep the retried step small. A step that does three things cannot repeat one of them.
</Tip>

## Timeouts

A Function step and a nested-flow step time out after **20 seconds** unless you set `timeout`. An HTTP Request step has no timeout of its own until you set one — a slow endpoint will hold the run open.

Set `timeout` on anything that leaves the platform. A step with no bound is the usual cause of a run that neither finishes nor fails.

## Failures that do not look like failures

Three things go wrong quietly. All three leave the run in status `success`.

**A function that returns an error object.** Most built-in functions catch their own errors and return `{"error": "…"}`. The invocation succeeded, so the step succeeded, and the next step reads an error object where it expected data. Branch on `$.STEP_ID.error` or `$.STEP_ID.status_code` when the result matters. See [Functions](/flows/functions/overview#how-a-function-fails).

**A JSONPath expression that matches nothing.** It resolves to `[]`, not `null` and not an error. A field name typo therefore produces an empty array that flows on downstream. Test with `Array.isArray(x) && x.length === 0`, not for a missing key.

**A misspelled rules operator.** The [rules engine](/advanced/rules/overview) drops the fact entirely and produces no error, no warning and no value. The flow continues with the fact simply absent, which usually shows up much later as a condition taking the wrong branch. Copy operator names rather than typing them.

## Controlling how often a flow runs

The gear icon in the flow editor toolbar opens **Flow options**, where **Run Type** changes how concurrent triggers are handled.

| Run Type | Behaviour | Use it when |
|---|---|---|
| *(none)* | Every trigger starts a run immediately, in parallel. | The default. Runs are independent. |
| **Debounced** | Runs matching the same **Debounce On** key collapse into one. The wait restarts on each new trigger, up to **Debounce Max**. | A source that fires in bursts — a record saved five times in a minute. |
| **Ordered** | Runs matching the same **Order On** key are queued and executed one after another. | Two runs for the same customer or record must not race. |

**Debounce On** and **Order On** are JSONPath expressions resolved against the trigger, so `$.trigger.customer_id` gives you one queue per customer. Both times are in **nanoseconds**: five seconds is `5000000000`.

<Note>
A debounced or ordered trigger returns straight away with a message rather than a tracking ID, because the run has not started yet. Anything expecting a synchronous result — an HTTP Request trigger answering its caller — should not use either.
</Note>

## Secrets

Put `SECRET::<name>::` anywhere in a node's configuration and the platform substitutes the value **once, before the first step runs**. That is the right way to reach a credential from a flow, and it is better than a step that fetches one, because the value never becomes a step result.

- A name containing a `.` is refused. Account-shared secrets have plain names.
- `SECRET::user.<KEY>::` resolves against your own identity for a personal secret.
- Step results are stored and shown in Monitoring. A credential that passes through a step's result is visible to anyone who can read the run.

## The limits worth knowing

| Limit | Value |
|---|---|
| Attempts per step | 5, whatever you configure |
| Backoff | Constant, no exponential growth |
| Default timeout, Function and nested-flow steps | 20 seconds |
| Default timeout, HTTP Request step | None until you set one |
| Messages folded by `aggregate-stream-items` | 1,000 |
| Default page size, `list-kv-bucket-items` | 100 |
| Default page size, `list-object-keys` | 500 |
| Reserved step IDs | `trigger`, `static`, `RESOLVE_SUCCESS`, `RESOLVE_ERROR` |

## Before you publish

- **Test the draft.** The editor's **Test** control runs the draft with a payload you type. It does not exercise the trigger.
- **Then publish.** Editing changes the draft only. A flow that behaves correctly under test keeps running its old published version until you publish.
- **Check a trigger survived the publish.** A trigger belongs to the flow version it was created on — see each [trigger page](/flows/triggers/overview).
- **Watch the first live runs in Monitoring.** Step results are recorded per run, which is the only place a silent failure becomes visible.
