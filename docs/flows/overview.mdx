# Flows

A **flow** is a graph of steps that runs when something triggers it. Each step does one thing — call an API, run an assistant, reshape data, decide what happens next — and stores its result where later steps can read it.

```
trigger  →  steps  →  result
```

- A [**trigger**](/flows/triggers/overview) starts the run. Whatever it receives becomes `$.trigger`.
- [**Steps**](/flows/steps/overview) do the work. Each stores its result under its own step ID.
- Steps read each other's results with [**variable mapping**](/advanced/variable-mapping/overview) — any string beginning with `$.`.

---

## How a run behaves

Four things are worth knowing before you build anything.

<AccordionGroup>
  <Accordion title="Steps do not run in sequence" icon="diagram-project">
    The runner is a concurrent graph executor. Every step with no incoming edge starts at once, and a step starts as soon as all of its predecessors have finished. Independent branches run in parallel.
  </Accordion>

  <Accordion title="A Condition's outcome decides what runs next" icon="code-branch">
    Arrows in the editor are not routing. A [Condition step](/flows/steps/condition) names the step IDs to run — one, several, or the reserved `RESOLVE_SUCCESS` / `RESOLVE_ERROR` to end the run. A line no outcome names is decoration.
  </Accordion>

  <Accordion title="The first error ends the whole run" icon="triangle-exclamation">
    There is no per-step error branch. The failing step records the error, the run is cancelled, and anything still in flight is abandoned. Results from steps that already finished are kept. See [Building Reliable Flows](/flows/best-practices).
  </Accordion>

  <Accordion title="Editing changes the draft, not the live flow" icon="pen-to-square">
    **Save** keeps your work. **Publish** is what makes it take effect. Testing in the editor runs the draft, so a flow that behaves correctly under test can still be running its old published version until you publish.
  </Accordion>
</AccordionGroup>

## What a step can read

Every step payload is resolved before the step runs. The data it can select from has these top-level keys and nothing else:

| Key | Contents |
|---|---|
| `trigger` | The payload that started the run |
| `static` | The flow's Static data |
| `context` | Context variables passed in on the run request |
| `env` | `auth_token`, `run_id` and `headers` for this run |
| *step ID* | The result of a step that has already finished |

```
$.trigger.customer.email
$.GET_ORDER.data.total
$.env.run_id
```

<Warning>
A path that matches nothing resolves to an **empty array**, not `null`. `$.trigger.nope` becomes `[]`.
</Warning>

## Building one

<Steps>
  <Step title="Create a flow">
    Flows live in collections. Create one from the Flows list.
  </Step>
  <Step title="Add a trigger">
    Pick how the flow starts — a URL, a schedule, an email address, a form on your site. See [Triggers](/flows/triggers/overview).
  </Step>
  <Step title="Add steps">
    Drag in the steps that do the work and wire them together. See [Steps](/flows/steps/overview).
  </Step>
  <Step title="Test the draft">
    **Test** runs the draft against a payload you type, standing in for `$.trigger`.
  </Step>
  <Step title="Publish">
    Publishing is what makes the flow live. Watch the first real runs under **Monitoring**.
  </Step>
</Steps>
