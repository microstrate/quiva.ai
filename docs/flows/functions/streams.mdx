# Stream Functions

A stream is an append-only log of messages. Each message is published to a **subject** — a dotted string such as `orders.ORD-001.created` — and a stream stores every message whose subject matches one of the patterns it was created with.

Nine functions are available to a [Function step](/flows/steps/functions):

| Function | Does |
|---|---|
| `create-stream` | Create a stream over a set of subject patterns |
| `publish-message-to-stream` | Publish one message |
| `get-item-from-stream` | Read messages on one subject |
| `search-stream-items` | Read messages matching a subject pattern |
| `aggregate-stream-items` | Fold a subject's messages into a single object |
| `list-streams` | List the account's streams |
| `unset-message-to-stream` | Publish a control message removing a path |
| `tombstone-message-to-stream` | Publish a control message ending a fold |
| `poison-pill-message-to-stream` | Publish a control message resetting a fold |

<Note>
These functions **write and read**. Nothing here consumes a stream as it fills. To start a flow when a message arrives, use a [stream trigger](/flows/triggers/stream-triggers).
</Note>

---

## Subjects and patterns

A subject is dot-separated. Two wildcards are available in the patterns you give `create-stream` and `search-stream-items`:

| Pattern | Matches |
|---|---|
| `orders.ORD-001.created` | that subject exactly |
| `orders.*.created` | one token in that position |
| `orders.>` | everything below `orders` |

`get-item-from-stream` takes a subject, not a pattern. Use `search-stream-items` when you want to match across many.

<Warning>
**Sanitise anything you interpolate into a subject.** A subject token built from user input — an email address, a filename — can carry characters that break routing. Map it to an ID first.
</Warning>

## create-stream

<ParamField path="name" type="string" required>
Stream name. Must be unique in the account.
</ParamField>

<ParamField path="subjects" type="array" required>
The subject patterns this stream stores. **Plural.** A payload using `subject` creates a stream that stores nothing.
</ParamField>

<ParamField path="description" type="string">
Free text shown alongside the stream.
</ParamField>

<ParamField path="retention" type="string">
`"limits"`, `"interest"` or `"workqueue"`. Default `"limits"` — messages stay until a size or age limit removes them. Lower case; a capitalised value is rejected.
</ParamField>

<ParamField path="storage" type="string">
`"file"` or `"memory"`. Default `"file"`. Lower case.
</ParamField>

<ParamField path="max_age" type="integer">
Maximum age of a retained message, **in nanoseconds**. One day is `86400000000000`.
</ParamField>

<ParamField path="max_bytes" type="integer">
Maximum total size of the stream in bytes.
</ParamField>

<ParamField path="max_msgs" type="integer">
Maximum number of messages retained.
</ParamField>

<ParamField path="max_msgs_per_subject" type="integer">
Maximum retained per subject. Set to `1` for a stream that only ever holds the latest state per subject.
</ParamField>

<ParamField path="max_msg_size" type="integer">
Maximum size of a single message in bytes.
</ParamField>

<ParamField path="num_replicas" type="integer">
Copies kept across the cluster. Default `1`, maximum `5`.
</ParamField>

<ParamField path="duplicate_window" type="integer">
Window in nanoseconds within which duplicate message IDs are rejected. Server default is two minutes.
</ParamField>

**Payload**

```json
{
  "name": "order-events",
  "subjects": ["orders.>"],
  "description": "Every order lifecycle event",
  "max_age": 2592000000000000
}
```

**Returns**

```json
{ "status_code": 200, "body": { "message": "success" } }
```

A name that already exists, or subjects that overlap an existing stream, comes back as `{"status_code": 409, "body": {"error": "..."}}`.

<Note>
The editor's form for this function also offers `re_publish` and a string `placement`. The configuration the platform reads names those `republish` and expects `placement` to be an object, so neither takes effect as the form presents them.
</Note>

## publish-message-to-stream

Publishes one message to a subject. Every stream whose patterns match that subject stores a copy. A subject no stream covers is an error — see [Failure](#failure).

<ParamField path="subject" type="string" required>
The subject to publish to.
</ParamField>

<ParamField path="value" type="object | string" required>
The message. An object is stored as JSON; a string is stored verbatim.
</ParamField>

**Payload**

```json
{
  "subject": "orders.ORD-001.created",
  "value": { "id": "$.trigger.order_id", "total": "$.trigger.total", "status": "created" }
}
```

**Returns** — for an object value:

```json
{ "status_code": 200, "body": { "body": { "stream": "order-events", "seq": 412 } } }
```

and for a string value:

```json
{ "status_code": 200, "body": { "message": "success" } }
```

Two things happen to an **object** value on the way in, and neither happens to a string:

- Any `stream` or `subject` key inside the object is removed.
- A `type` key is added with the value `"created"` if the object does not already have one. That key is what [aggregation](#aggregate-stream-items) reads, so leave it alone unless you mean to publish a control message.

## get-item-from-stream

Reads the messages stored on one subject.

<ParamField path="stream" type="string" required>
Stream to read from.
</ParamField>

<ParamField path="subject" type="string" required>
Exact subject. No wildcards.
</ParamField>

<ParamField path="limit" type="integer">
Maximum messages to return. Setting this switches to a sequence-bounded read.
</ParamField>

<ParamField path="from_sequence" type="integer">
Sequence to start from.
</ParamField>

<ParamField path="to_sequence" type="integer">
Sequence to stop at.
</ParamField>

**Payload**

```json
{ "stream": "order-events", "subject": "orders.ORD-001.created", "limit": 20 }
```

**Returns**

```json
{
  "status_code": 200,
  "body": {
    "body": {
      "results": [
        { "id": "ORD-001", "total": 35, "status": "created", "type": "created",
          "subject": "orders.ORD-001.created", "sequence": 412, "modified": 1755680042 }
      ],
      "results_total": 1
    },
    "metadata": { "subject": "orders.ORD-001.created", "total_messages": 1204, "next_sequence": 0 }
  }
}
```

Each result **is the published message**, with `subject`, `sequence` and `modified` added to it. There is no wrapper object to unpick.

<Warning>
**A message that is not a JSON object is skipped, silently.** Anything published as a plain string is dropped from the results with no error and no gap in `results_total`. Read those with `search-stream-items`, which returns raw values.
</Warning>

<Warning>
**Only `limit` reliably bounds the read.** The node decides between a plain read and a sequence-bounded read by looking for camel-cased `fromSequence` / `toSequence`, but the form and the schema name those fields `from_sequence` and `to_sequence`. Passing either on its own therefore does nothing. Send `limit` as well and both are honoured.
</Warning>

When `limit` is set and a further page exists, `metadata.next_sequence` carries the sequence to resume from; it is `0` when you have reached the end.

## search-stream-items

Reads messages matching a subject **pattern**, with their raw values.

<ParamField path="stream" type="string" required>
Stream to search.
</ParamField>

<ParamField path="search" type="string" required>
A subject pattern, wildcards allowed. This matches on the **subject**, not on message content — there is no full-text search here.
</ParamField>

<ParamField path="limit" type="integer" required>
Maximum messages to return.
</ParamField>

**Payload**

```json
{ "stream": "order-events", "search": "orders.*.created", "limit": 100 }
```

**Returns**

```json
{
  "status_code": 200,
  "body": {
    "body": {
      "results": [
        { "created": 1755680042, "subject": "orders.ORD-001.created", "value": "{\"id\":\"ORD-001\",\"total\":35}" }
      ],
      "results_total": 1
    },
    "metadata": { "stream": "order-events", "limit": 100, "search": "orders.*.created" }
  }
}
```

`value` is always the raw stored text. Parse it in an [Eval step](/flows/steps/eval) if you need the structure.

## aggregate-stream-items

Reads every message on a subject and folds them, oldest first, into one object. This is how a stream is used to hold state: publish changes as they happen, aggregate to get the current picture.

<ParamField path="stream" type="string" required>
Stream to read from.
</ParamField>

<ParamField path="subject" type="string" required>
A subject pattern, wildcards allowed. Up to 1,000 messages are folded.
</ParamField>

**Payload**

```json
{ "stream": "order-events", "subject": "orders.ORD-001.>" }
```

**Returns** — the folded object, in place of the usual result list:

```json
{
  "status_code": 200,
  "body": {
    "body": { "id": "ORD-001", "total": 35, "status": "shipped", "type": "created" },
    "metadata": { "stream": "order-events", "limit": 1000, "search": "orders.ORD-001.>" }
  }
}
```

### The fold

Each message is read in order and applied by its `type`:

| `type` | Effect |
|---|---|
| `"tombstoned"` | Folding **stops**. Nothing after this message is applied. |
| `"poison-pilled"` | The accumulated object is discarded and folding restarts empty. |
| `"unset"` | The paths named in the message's `path` (or `paths`) are removed. |
| anything else | The message is deep-merged into the accumulated object. |

A merge is a deep merge, so a later message can change one nested field without restating the rest — but it cannot remove a field. That is what `unset` is for.

Aggregation reads the fold markers back out of the messages, so the `type` key that `publish-message-to-stream` adds is part of the contract. A message that is not valid JSON breaks the fold.

## unset-message-to-stream

Publishes a control message that removes one or more paths from an aggregate. It does not delete anything from the stream — the removal is applied when the subject is next folded.

<ParamField path="subject" type="string" required>
Subject to publish to. Use the same subject the values were published on.
</ParamField>

<ParamField path="path" type="string">
Dotted path to remove, for example `"customer.phone"`. An array of paths under `paths` is also accepted.
</ParamField>

**Payload**

```json
{ "subject": "orders.ORD-001.updated", "path": "customer.phone" }
```

The message published is your payload with `type: "unset"` added.

---

## tombstone-message-to-stream

Publishes a control message that stops the fold. Everything published to the subject afterwards is ignored by `aggregate-stream-items`, so this is how you mark an aggregate closed.

<ParamField path="subject" type="string" required>
Subject to publish to.
</ParamField>

```json
{ "subject": "orders.ORD-001.closed" }
```

The message published is your payload with `type: "tombstoned"` added.

---

## poison-pill-message-to-stream

Publishes a control message that discards everything folded so far and starts again from empty. Use it to reset an aggregate without deleting its history.

<ParamField path="subject" type="string" required>
Subject to publish to.
</ParamField>

```json
{ "subject": "orders.ORD-001.reset" }
```

The message published is your payload with `type: "poison-pilled"` added.

---

## list-streams

Lists every stream in the account. Takes no parameters — an empty payload `{}` is correct.

The streams behind key-value and object buckets are filtered out of this listing, so a bucket you created will not appear here.

**Returns**

```json
{
  "status_code": 200,
  "body": {
    "body": {
      "results": [
        { "name": "order-events", "description": "Every order lifecycle event",
          "subjects": ["orders.>"], "messages_total": 1204, "created": 1755600000 }
      ],
      "results_total": 1
    }
  }
}
```

## Failure

Every function on this page catches its own errors and returns `{"error": "<message>"}`. **That is a successful step** — the run continues and the next step reads an object with an `error` key where it expected data.

A publish to a subject that no stream covers does not quietly vanish — it retries, then comes back as an error in the body. It is still a successful step, so check the result rather than assuming the message landed.

See [Best practices](/flows/best-practices) for what a part-completed run leaves behind.
