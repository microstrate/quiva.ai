# Functions

A **Function step** calls one built-in function. You pick the function from a list, write a JSON **Payload** for it, and the value it returns becomes the step's result.

There are 31 built-in functions. They fall into four groups:

<CardGroup cols={2}>
  <Card title="Key-Value Storage" icon="database" href="/flows/functions/key-value">
    Five functions for buckets of small values addressed by key
  </Card>

  <Card title="Object Storage" icon="box" href="/flows/functions/object-storage">
    Five functions for buckets of larger objects — files, documents, exports
  </Card>

  <Card title="Streams" icon="stream" href="/flows/functions/streams">
    Nine functions for append-only message streams and their aggregation
  </Card>

  <Card title="Utilities" icon="shuffle" href="/flows/functions/utility">
    Nine functions for encoding, templating, format conversion and file transfer
  </Card>
</CardGroup>

The remaining three — `Delay`, `HTTP` and `Rules` — are in the same catalogue but have their own step types. Use the [Delay](/flows/steps/delay), [HTTP Request](/flows/steps/http-request) and [Rules](/flows/steps/rules) steps rather than a Function step, because those steps give you a proper editor for the same operation.

## Every function

Names are exactly as they appear in the picker, including capitalisation.

| Function | Group | Does |
|---|---|---|
| `create-key-value-bucket` | Key-value | Create a bucket |
| `put-kv-item` | Key-value | Write one key |
| `get-kv-bucket-item` | Key-value | Read one key |
| `list-key-value-buckets` | Key-value | List the account's buckets |
| `list-kv-bucket-items` | Key-value | List keys and values in a bucket |
| `create-object-store-bucket` | Object | Create a bucket |
| `put-object-by-key` | Object | Write one object |
| `get-object-from-bucket` | Object | Read one object |
| `list-object-store-buckets` | Object | List the account's buckets |
| `list-object-keys` | Object | List object metadata in a bucket |
| `create-stream` | Stream | Create a stream over a set of subjects |
| `publish-message-to-stream` | Stream | Publish one message to a subject |
| `get-item-from-stream` | Stream | Read messages on a subject |
| `search-stream-items` | Stream | Read messages matching a subject pattern |
| `aggregate-stream-items` | Stream | Fold a subject's messages into one object |
| `list-streams` | Stream | List the account's streams |
| `unset-message-to-stream` | Stream | Publish a control message removing a path |
| `tombstone-message-to-stream` | Stream | Publish a control message ending a fold |
| `poison-pill-message-to-stream` | Stream | Publish a control message resetting a fold |
| `base64-encode` | Utility | Encode text or an object to base64 |

## Configuring a Function step

The node editor has two tabs, and two more in advanced mode:

| Tab | Contents |
|---|---|
| **General** | Step name and step ID |
| **Function** | The **Function** dropdown, and a form generated from that function's input schema. Required. |
| **Response Map** | A JSONPath mapping applied to the result before it is stored. Advanced mode only. |
| **Advanced Settings** | Timeout, attempts, backoff, ignored response codes, flat map. Advanced mode only. |

The form on the **Function** tab is built from the function's declared input schema, so the fields you see are the parameters that function accepts. **JSON Editor** opens the same payload as raw JSON, validated against that schema.

The payload is sent to the function exactly as written, after JSONPath resolution. Any string beginning with `$.` is resolved against the run's data first — see [Variable Mapping](/advanced/variable-mapping/overview).

<Note>
There is no request envelope. The payload *is* the function's input. A payload of `{"bucket": "orders", "key": "ord_88"}` reaches `get-kv-bucket-item` as exactly that object.
</Note>

## Reading the result

The result is stored flat under the step's ID. If the step ID is `GET_ORDER`:

```
$.GET_ORDER.status_code
$.GET_ORDER.body.body.value
```

There is no `.output` or `.result` wrapper.

Most functions return the same envelope:

```json
{
  "status_code": 200,
  "body": { "body": { }, "metadata": { } }
}
```

Write functions return `{"status_code": …, "body": {"message": …}}` or `{"status_code": …, "body": {"error": …}}` instead, and the pure utilities (`base64-encode`, `Handlebars Template`, `JSON-XML`, `SFTP`) return a bare string.

## How a function fails

<Warning>
**A function that returns an error object still counts as a successful step.** Several functions handle their own errors by returning `{"error": "…"}` rather than throwing. The invocation succeeded, so the run carries on and the next step reads `{"error": …}` where it expected data.

Test for it explicitly with a [Condition step](/flows/steps/condition) on `$.STEP_ID.error`, or on `$.STEP_ID.status_code` where the function returns one.
</Warning>

Three things do end the run:

- The function throws and the runtime cannot catch it.
- The invocation itself fails — the function could not be reached, or did not run.
- The call exceeds its timeout — 20 seconds unless you set one in **Advanced Settings**.

An inner `status_code` of 409 or 404 in the body is *not* one of these. The invocation succeeded; the step succeeded; only the operation did not.

There is no per-step error branch. The first step that errors cancels the whole run — see [Building Reliable Flows](/flows/best-practices).
