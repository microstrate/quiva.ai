# Webhook Trigger

A webhook trigger gives a flow a URL that an outside service can POST to. The request body becomes `$.trigger`, the flow runs, and the response goes back to the caller.

Underneath, it is a gateway mapping pointed at your flow — the same machinery as the [HTTP Request trigger](/flows/triggers/http-request). The difference is that the webhook trigger generates the path for you, opens it to the public, and hides the tuning controls.

| | Webhook | HTTP Request |
|---|---|---|
| Path | Generated: `/webhook/<collection>/<flow>` | You type it |
| Public by default | Yes | No |
| Editable settings | API key only | Public URL, timeout, requests/second, invocation type, allowed hosts |

<Tip>
If you want to choose the path, keep the endpoint authenticated, or set a timeout, use the [HTTP Request trigger](/flows/triggers/http-request) instead. Everything on this page applies to it too.
</Tip>

---

## Creating one

Add a **Webhook** trigger from the **Add Node** panel. A **Create Webhook** dialogue opens showing the URL that will be created, a **Public** / **Secure** pill, and — if your account has more than one gateway — a gateway to pick. Press **Create**.

The URL is fixed. It is built from your flow's own identifiers and there is nothing to type.

---

## The URL

```
https://<your-gateway-host>/webhook/<collection-id>/<flow-id>
```

`<your-gateway-host>` is your own gateway's hostname — a subdomain of the platform's API host, unique to that gateway. It is **not** `api.quiva.ai`, and there is no shared webhook host that every account posts to.

<Warning>
Do not construct the URL by hand. Open the webhook trigger node and copy the **Full URL** row — that is the only reliable source.
</Warning>

---

## Calling it

**POST only**, with a JSON body. The method is not configurable on the trigger.

```bash
curl -X POST "https://<your-gateway-host>/webhook/<collection-id>/<flow-id>" \
  -H "Content-Type: application/json" \
  -d '{"type":"payment.succeeded","data":{"object":{"id":"pi_3Q","amount":2500}}}'
```

Against a secured webhook, add the key:

```bash
curl -X POST "https://<your-gateway-host>/webhook/<collection-id>/<flow-id>" \
  -H "Content-Type: application/json" \
  -H "x-api-key: <your-api-key>" \
  -d '{"type":"payment.succeeded"}'
```

The header is `x-api-key`. There is no query-string form. Keys issued from a trigger panel are *restricted* keys — they carry an `msr-` prefix and are valid for that one endpoint and method only.

<Warning>
**The body must be valid JSON.** A body that fails to parse currently comes back as **200 OK** carrying a plain-text parse error, not a 4xx. A sender that only checks the status code will believe the call succeeded. Form-encoded (`application/x-www-form-urlencoded`) and multipart bodies fail this way, so a service that cannot send JSON cannot drive a webhook trigger.
</Warning>

<Warning>
**Query parameters are dropped.** A sender that puts information in the query string loses it — it does not reach `$.trigger` and is not recoverable from `$.env.headers`.
</Warning>

## Security

A webhook is created **public** — anyone who knows the URL can run your flow. (The exception: if an API key named after this webhook's path already exists on the account, it is created secure.) The trigger panel says so:

> This webhook is public and insecure. We recommend deleting it and creating a secured webhook instead.

The **Create Webhook** dialogue has no control to change this — the pill is a label, not a switch.

To close a webhook off, turn off **Public URL** on its gateway mapping under **Resources → Gateways**. The trigger node's **Security** section then appears, and from there:

<Steps>
  <Step title="Set an expiry">
    **Expiry (days)** defaults to 365.
  </Step>
  <Step title="Generate API Key">
    Copy the key immediately — it is shown once, and it is scoped to this endpoint alone.
  </Step>
</Steps>

There is no regenerate. Rotating means deleting the key and generating a new one, which invalidates the old one at once.

<Tip>
An [HTTP Request trigger](/flows/triggers/http-request) is authenticated from the start and exposes the **Public URL** toggle on the node itself. If the endpoint should be private, that is the easier path.
</Tip>

<Warning>
There is **no signature verification** — no Stripe, GitHub, Slack or custom HMAC checking, and no secret field. There is also no event filtering: every request that reaches the URL starts the flow, and you filter on `$.trigger` in a [Condition](/flows/steps/condition) step if you only want some of them. Nothing responds to a service's URL-verification challenge either.
</Warning>

## Reading the request

`$.trigger` is the raw request body, unwrapped and with nothing added.

For this body:

```json
{
  "type": "payment.succeeded",
  "data": { "object": { "id": "pi_3Q", "amount": 2500, "currency": "gbp" } }
}
```

| Expression | Resolves to |
|---|---|
| `$.trigger.type` | `"payment.succeeded"` |
| `$.trigger.data.object.amount` | `2500` |
| `$.trigger.data.object` | the whole object |
| `Payment \|$.trigger.data.object.id\| for \|$.trigger.data.object.amount` | `"Payment pi_3Q for 2500"` |

Request headers are on `$.env.headers`, flattened to strings and keyed exactly as they arrived:

```
$.env.headers.user-agent
$.env.headers["content-type"]
```

<Warning>
There is no `$.trigger.headers`, no `$.trigger.webhook_id` and no `$.trigger.received_at`. Nothing about the request is added to the payload — if you need the delivery time, take it from a header the sender set, or generate one in a step.
</Warning>

---

## The response

The caller waits for the flow and gets back JSON:

```json
{
  "tracking_id": "…",
  "status": "…",
  "result": { }
}
```

`result` is every step's output by default. Set the flow's **Final Response Mapping** (in the flow's settings) to a JSONPath object and `result` becomes exactly that instead — the usual way to hand a sender the shape it expects.

<Note>
There is no `executionId`, no `executionTime` and no `error.code` envelope. A run that errors still returns this shape; the failure shows in `status` and in **Monitoring**.
</Note>

## Draft and published flows

**A webhook always runs the published flow.** The mapping is created against the published subject even when you build it on a draft, so:

- Before the flow's first publish, calls arrive with nothing to run.
- Editing and pressing **Save** changes nothing about what the webhook executes. Press **Publish**.

This differs from most other triggers, which bind to whichever version was open when you created them.

<Note>
**What runs after the trigger is decided by each step's outcome, not by the arrows in the editor.** A Condition step's outcome names the step IDs to run next — one, several (they start at the same time), or the reserved `RESOLVE_SUCCESS` / `RESOLVE_ERROR` to end the run. A line drawn between two steps that no outcome names is decoration.
</Note>

## Troubleshooting

<AccordionGroup>
  <Accordion title="The sender reports 200 but the flow never ran">
    Almost always a body that is not valid JSON. Parse failures return 200 with a plain-text error in the body — read the body, not the status code.
  </Accordion>

  <Accordion title="401 or 403">
    The webhook is secured and the caller is not sending `x-api-key`, or the key has expired. Keys default to a 365-day expiry.
  </Accordion>

  <Accordion title="The URL 404s">
    Check the flow has been published at least once. Then re-copy the **Full URL** from the trigger node rather than trusting a URL written down earlier.
  </Accordion>

  <Accordion title="The flow ran but a step read nothing">
    `$.trigger` is the request body with nothing wrapped around it, so a path that assumed a wrapper resolves to `[]`. Open the run in **Monitoring** and read the recorded trigger.
  </Accordion>

  <Accordion title="Only some events should start the flow">
    All of them do. Put a Condition step first and branch on a field of `$.trigger`.
  </Accordion>

  <Accordion title="A browser call is blocked by CORS">
    Add the site's origin under **Allowed Hosts** on an HTTP Request trigger. That list is a property of your account's gateway, shared by every endpoint on it — it is not per-trigger.
  </Accordion>
</AccordionGroup>
