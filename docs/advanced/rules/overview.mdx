## What the Rules step does

The Rules step derives new values from data your flow already has. You give it
**facts** — a flat object of inputs — and **rules** — an object saying what to
calculate from them. It works out the order to evaluate in and returns a flat
object of results for the rest of the flow to use.

It is closest in spirit to a set of spreadsheet formulas: each rule names the
value it produces, and rules that depend on one another sort themselves out.

Use it when the logic is a calculation or a decision made from values you already
have — pricing and discount bands, eligibility checks, validating a submission,
scoring, working out a due date, or picking a label. Reach for the
[Eval step](/flows/steps/eval) instead when you need real code, and for the
[Condition step](/flows/steps/condition) when the outcome is which branch of the
flow runs next.

## A first example

**Facts**

```json
{
  "orderTotal.value": 75,
  "isPremiumMember.value": false
}
```

**Rules**

```json
{
  "qualifiesForFreeShipping.value": {
    "operator": "or",
    "input": [
      { "operator": ">=", "input": ["@fact:orderTotal.value", 50] },
      { "operator": "=", "input": ["@fact:isPremiumMember.value", true] }
    ]
  }
}
```

**Output**

```json
{
  "qualifiesForFreeShipping.value": true
}
```

Three things are worth noticing. Rules read facts by name with `@fact:`. Operators
nest — the `or` takes two comparisons as its inputs. And the key on the left is
just a name you chose; it becomes a fact that later rules can read.

## A worked example

A discount band, the discount it implies, and the resulting price.

**Facts**

```json
{ "orderTotal.value": 650 }
```

**Rules**

```json
{
  "discountRate.value": [
    { "condition": { "operator": ">=", "input": ["@fact:orderTotal.value", 1000] }, "outcome": 0.15 },
    { "condition": { "operator": "between", "input": ["@fact:orderTotal.value", [500, 999.99]] }, "outcome": 0.1 },
    { "condition": { "operator": "between", "input": ["@fact:orderTotal.value", [200, 499.99]] }, "outcome": 0.05 },
    { "outcome": 0 }
  ],
  "discountAmount.value": {
    "operator": "*",
    "input": ["@fact:orderTotal.value", "@fact:discountRate.value"]
  },
  "payable.value": {
    "operator": "-",
    "input": ["@fact:orderTotal.value", "@fact:discountAmount.value"]
  }
}
```

**Output**

```json
{
  "discountRate.value": 0.1,
  "discountAmount.value": 65,
  "payable.value": 585
}
```

`discountRate.value` is an if/else ladder: cells are tried in order and the first
matching condition wins, with the last cell as the default. The two rules below
it reference it by name, and the engine works out that they must run after it.

## What to know before you build one

<CardGroup cols={2}>
  <Card title="Some failures are silent" icon="triangle-exclamation" href="/advanced/rules/core-concepts#when-a-rule-produces-nothing">
    A misspelled operator fails the step and names itself. A ladder that matches
    nothing, a calculation that produces `NaN` and an outcome of `null` do not —
    the fact is simply absent and the flow carries on.
  </Card>
  <Card title="Dots in rule names need brackets" icon="link" href="/advanced/rules/core-concepts#reading-the-output-in-later-steps">
    A rule named `finalPrice.value` is read downstream as
    `$.rules_1['finalPrice.value']`. The dotted form resolves to nothing.
  </Card>
  <Card title="The operator list is fixed" icon="list-check" href="/advanced/rules/operations-reference">
    The engine has 96 registered operator names — many of them aliases of each
    other — plus `fact`. Anything outside that list does not exist, however
    reasonable it sounds.
  </Card>
  <Card title="Publish before testing" icon="rocket" href="/flows/overview">
    Editing a flow changes its draft. A running flow keeps using the published
    version until you publish again.
  </Card>
</CardGroup>
