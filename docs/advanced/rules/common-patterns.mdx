Every pattern below was run through the engine. The facts, the rules and the
output are the real ones — copy them, change the names, and they will behave the
same way.

## Banded rates

The commonest shape: pick a rate from a band, apply it, report the result. The
ladder is tried top to bottom and the first matching condition wins, so put the
bands in order and finish with a cell that has no condition.

**Facts**

```json
{ "orderTotal.value": 650 }
```

**Rules**

```json
{
  "discountRate.value": [
    { "condition": { "operator": ">=", "input": ["@fact:orderTotal.value", 1000] }, "outcome": 0.15 },
    { "condition": { "operator": "between", "input": ["@fact:orderTotal.value", [500, 999.99]] }, "outcome": 0.1 },
    { "condition": { "operator": "between", "input": ["@fact:orderTotal.value", [200, 499.99]] }, "outcome": 0.05 },
    { "outcome": 0 }
  ],
  "discountAmount.value": { "operator": "*", "input": ["@fact:orderTotal.value", "@fact:discountRate.value"] },
  "payable.value": { "operator": "-", "input": ["@fact:orderTotal.value", "@fact:discountAmount.value"] }
}
```

**Output**

```json
{
  "discountRate.value": 0.1,
  "discountAmount.value": 65,
  "payable.value": 585
}
```

`between` takes its bounds as a **nested array**. Written flat as
`[value, 500, 999.99]` it returns `false` for everything, silently — which in a
ladder means the band is never reached.

## Validation with one message

Test each requirement as its own rule, combine them, and use a second ladder to
pick the message. Ordering the message ladder puts the requirements in the order
you want them reported.

**Facts**

```json
{ "email.value": "sam.example.com", "fullName.value": "Sam Okonkwo" }
```

**Rules**

```json
{
  "emailValid.value": { "operator": "stringContains", "input": ["@fact:email.value", "@"] },
  "nameProvided.value": { "operator": "notEmpty", "input": "@fact:fullName.value" },
  "formValid.value": { "operator": "and", "input": ["@fact:emailValid.value", "@fact:nameProvided.value"] },
  "validationMessage.value": [
    { "condition": { "operator": "not", "input": "@fact:nameProvided.value" }, "outcome": "Enter your full name." },
    { "condition": { "operator": "not", "input": "@fact:emailValid.value" }, "outcome": "Enter a valid email address." },
    { "outcome": "Looks good." }
  ]
}
```

**Output**

```json
{
  "emailValid.value": false,
  "nameProvided.value": true,
  "formValid.value": false,
  "validationMessage.value": "Enter a valid email address."
}
```

Note how `not` is given its input unwrapped — `"input": "@fact:nameProvided.value"`
rather than `["@fact:nameProvided.value"]`. `not` is the one operator that does
not wrap a scalar input, and given an array it returns an array of booleans,
which is always truthy.

## Every reason, not just the first

When you want the full list rather than the first match, use `generateArray`.
Each input is `[test, valueWhenTrue]`; the tests that fail contribute nothing.

**Facts**

```json
{ "score.value": 540, "monthsActive.value": 9, "openIssues.value": ["INC-2"] }
```

**Rules**

```json
{
  "declineReasons.value": {
    "operator": "generateArray",
    "input": [
      [{ "operator": "<", "input": ["@fact:score.value", 600] }, "Score below threshold"],
      [{ "operator": "<", "input": ["@fact:monthsActive.value", 6] }, "Account too new"],
      [{ "operator": "notEmpty", "input": "@fact:openIssues.value" }, "Open issues outstanding"]
    ]
  },
  "declined.value": { "operator": "notEmpty", "input": "@fact:declineReasons.value" },
  "reasonText.value": { "operator": "join", "input": "@fact:declineReasons.value" }
}
```

**Output**

```json
{
  "declineReasons.value": ["Score below threshold", "Open issues outstanding"],
  "declined.value": true,
  "reasonText.value": "Score below threshold,Open issues outstanding"
}
```

<Note>
When no test passes, `generateArray` produces nothing and `declineReasons.value`
is **absent** from the output rather than an empty array. `notEmpty` still
returns `false`, so `declined.value` is correct — but a downstream step reading
the list must cope with the key not being there.
</Note>

## Scoring

Points from independent rules, summed, then banded. Keeping each contribution as
its own rule makes the total explainable when someone asks why a record scored
what it did.

**Facts**

```json
{ "monthsActive.value": 18, "plan.value": "team", "weeklySessions.value": 25 }
```

**Rules**

```json
{
  "tenurePoints.value": [
    { "condition": { "operator": ">=", "input": ["@fact:monthsActive.value", 24] }, "outcome": 30 },
    { "condition": { "operator": ">=", "input": ["@fact:monthsActive.value", 12] }, "outcome": 20 },
    { "outcome": 5 }
  ],
  "planPoints.value": {
    "operator": "map",
    "input": ["@fact:plan.value", { "business": 40, "team": 25, "starter": 10, "$default": 0 }]
  },
  "usagePoints.value": [
    { "condition": { "operator": ">", "input": ["@fact:weeklySessions.value", 20] }, "outcome": 30 },
    { "outcome": 0 }
  ],
  "score.value": {
    "operator": "+",
    "input": ["@fact:tenurePoints.value", "@fact:planPoints.value", "@fact:usagePoints.value"]
  },
  "band.value": [
    { "condition": { "operator": ">=", "input": ["@fact:score.value", 70] }, "outcome": "high" },
    { "condition": { "operator": ">=", "input": ["@fact:score.value", 40] }, "outcome": "medium" },
    { "outcome": "low" }
  ]
}
```

**Output**

```json
{
  "tenurePoints.value": 20,
  "planPoints.value": 25,
  "usagePoints.value": 30,
  "score.value": 75,
  "band.value": "high"
}
```

<Warning>
You cannot inline the ladders into the `+`. A `{condition, outcome}` object
placed inside an operator's `input` is not resolved — it survives as a raw
object, `+` parses it as `NaN` and discards it, and the total comes out as `0`
with no complaint. Each branch must be its own rule.
</Warning>

## Lookup tables

`map` turns a table into a rule. `$default` catches everything unlisted; without
it, and without a third input, a miss drops the fact entirely.

```json
{
  "regionRate.value": {
    "operator": "map",
    "input": ["@fact:region.value", { "uk": 0.2, "de": 0.19, "$default": 0 }]
  }
}
```

With `region.value` of `"fr"` the result is `0`.

An **array** key walks the table one level per element, which gives you a
two-dimensional lookup:

```json
{
  "rate.value": {
    "operator": "lookup",
    "input": [["uk", "standard"], { "uk": { "standard": 0.2, "reduced": 0.05 } }, 0]
  }
}
```

Result: `0.2`.

## Multi-condition eligibility

Name each test, then combine. This costs nothing at runtime — `and` receives
inputs that were all evaluated anyway — and it means the step's output shows you
which test failed.

**Facts**

```json
{ "monthsActive.value": 9, "plan.value": "team", "openIssues.value": [] }
```

**Rules**

```json
{
  "tenureOk.value": { "operator": ">=", "input": ["@fact:monthsActive.value", 6] },
  "planOk.value": { "operator": "inArray", "input": ["@fact:plan.value", ["team", "business"]] },
  "noOpenIssues.value": { "operator": "empty", "input": "@fact:openIssues.value" },
  "eligible.value": {
    "operator": "and",
    "input": ["@fact:tenureOk.value", "@fact:planOk.value", "@fact:noOpenIssues.value"]
  }
}
```

**Output**

```json
{
  "tenureOk.value": true,
  "planOk.value": true,
  "noOpenIssues.value": true,
  "eligible.value": true
}
```

Use `empty` rather than `not` for "has no items": an empty array is truthy, so
`not` on one returns `false`.

## Working with an array of objects

`jPath` pulls values out of an array fact. It returns an array, which arithmetic
operators accept directly.

**Facts**

```json
{
  "lines.value": [
    { "sku": "A", "price": 12.5, "qty": 2 },
    { "sku": "B", "price": 40, "qty": 1 }
  ]
}
```

**Rules**

```json
{
  "unitPrices.value": { "operator": "jPath", "input": ["@fact:lines.value", "$[*].price"] },
  "quantities.value": { "operator": "jPath", "input": ["@fact:lines.value", "$[*].qty"] },
  "itemCount.value": { "operator": "+", "input": "@fact:quantities.value" },
  "highestPrice.value": { "operator": "max", "input": "@fact:unitPrices.value" }
}
```

**Output**

```json
{
  "unitPrices.value": [12.5, 40],
  "quantities.value": [2, 1],
  "itemCount.value": 3,
  "highestPrice.value": 40
}
```

<Warning>
**Arithmetic is never element-wise.** Multiplying `unitPrices.value` by
`quantities.value` does not give you line totals — `*` flattens both arrays and
multiplies everything into a single scalar, `1200` in this case. There is no
operator that pairs two arrays. Use the wildcard pattern below, or compute the
totals before the flow reaches the Rules step.
</Warning>

Note also that `min` and `max` do not flatten. `"input": "@fact:unitPrices.value"`
works; `"input": ["@fact:unitPrices.value"]` sees one array, cannot parse it as a
number, and drops the fact.

## Counting

There is no length operator. `jPath` with `$.length` returns a one-element array,
and `+` reduces it to a number.

```json
{
  "tagCount.value": {
    "operator": "+",
    "input": { "operator": "jPath", "input": ["@fact:tags.value", "$.length"] }
  },
  "manyTags.value": { "operator": ">=", "input": ["@fact:tagCount.value", 3] }
}
```

With `tags.value` of `["billing", "urgent", "vip"]`: `3` and `true`.

## Per-element arithmetic with wildcard keys

When you genuinely need a calculation per item, flatten the data into keys of the
form `parent/index/child` and use a wildcard in the **rule key**. The engine
expands it into one rule per entry in the parent list.

**Facts**

```json
{
  "lines": "A,B",
  "lines/A/price": 12.5,
  "lines/A/qty": 2,
  "lines/B/price": 40,
  "lines/B/qty": 1
}
```

**Rules**

```json
{
  "lines/*/total": { "operator": "*", "input": ["@fact:lines/*/price", "@fact:lines/*/qty"] },
  "orderTotal.value": { "operator": "+", "input": "@fact:lines/*/total" }
}
```

**Output**

```json
{
  "lines/A/total": 25,
  "lines/B/total": 40,
  "orderTotal.value": 65
}
```

The parent list may be a comma-separated string as above, or an array. See
[wildcard fact keys](/advanced/rules/core-concepts#wildcard-fact-keys) for
nesting.

## Building a message

`stringTemplate` fills numbered placeholders in order. Inputs may be nested
operators, so formatting happens inline.

**Facts**

```json
{
  "firstName.value": "Sam",
  "plan.value": "team",
  "renewalDate.value": "2026-11-04T00:00:00Z"
}
```

**Rules**

```json
{
  "summary.value": {
    "operator": "stringTemplate",
    "input": [
      "{{1}}, your {{2}} plan renews on {{3}}.",
      "@fact:firstName.value",
      "@fact:plan.value",
      { "operator": "dateFormat", "input": ["@fact:renewalDate.value", "dd MMM yyyy"] }
    ]
  }
}
```

**Output**

```json
{ "summary.value": "Sam, your team plan renews on 04 Nov 2026." }
```

`concat` joins with a single space and `join` with a comma, neither of which is
configurable — `stringTemplate` is the only operator that gives you control over
the text between the parts.

## Dates

Durations are a number and a single case-sensitive letter: `y`, `M`, `w`, `d`,
`h`, `m`, `s`. `1M` is a month and `1m` is a minute. Spelled-out units are
ignored.

**Facts**

```json
{ "receivedAt.value": "2026-08-14T09:00:00Z" }
```

**Rules**

```json
{
  "dueDate.value": { "operator": "addDate", "input": ["@fact:receivedAt.value", "5d"] },
  "ageDays.value": {
    "operator": "dateDiff",
    "input": ["@fact:receivedAt.value", { "operator": "today", "input": [] }, "d"]
  },
  "overdue.value": { "operator": ">", "input": ["@fact:ageDays.value", 5] }
}
```

**Output**, run on 27 August 2026:

```json
{
  "dueDate.value": "2026-08-19T09:00:00.000Z",
  "ageDays.value": 12,
  "overdue.value": true
}
```

`dateDiff` returns `end - start`, so the order of the first two inputs decides
the sign.

## Guarding a calculation

Division by zero returns `NaN`, which drops the fact — so a rule that looks
harmless can leave a hole in the output. Guard it with a ladder.

**Facts**

```json
{ "total.value": 250, "count.value": 0 }
```

**Rules**

```json
{
  "average.value": [
    {
      "condition": { "operator": ">", "input": ["@fact:count.value", 0] },
      "outcome": { "operator": "/", "input": ["@fact:total.value", "@fact:count.value"] }
    },
    { "outcome": 0 }
  ]
}
```

**Output**

```json
{ "average.value": 0 }
```

The same applies to `*`: a `null` or missing input makes the whole result `NaN`.
`+` is the exception — it discards values it cannot parse and carries on.

## Clamping

`min` caps a value and `max` floors it. Read them as "no more than" and "no less
than".

```json
{
  "raw.value": { "operator": "*", "input": ["@fact:base.value", 1.5] },
  "capped.value": { "operator": "min", "input": ["@fact:raw.value", 500] },
  "floored.value": { "operator": "max", "input": ["@fact:capped.value", 100] }
}
```

With `base.value` of `420`: `630`, then `500`, then `500`.

## Defaults

A rule key ending `.defaultValue` automatically supplies the matching `.value`
when nothing else does.

```json
{ "slaHours.defaultValue": 24 }
```

**Output**

```json
{ "slaHours.defaultValue": 24, "slaHours.value": 24 }
```

A fact wins over the default, and so does an explicit `.value` rule.

<Warning>
The fallback is disabled by the *presence* of a `.value` rule, not by whether
that rule produces anything. A ladder with no default cell that matches nothing
leaves you with no `.value` at all. Reference the default explicitly if you want
both:

```json
{
  "priority.defaultValue": "normal",
  "priority.value": [
    { "condition": { "operator": "=", "input": ["@fact:severity.value", "high"] }, "outcome": "urgent" },
    { "outcome": "@fact:priority.defaultValue" }
  ]
}
```

With `severity.value` of `"low"` this returns `"normal"`.
</Warning>

## Extracting from text

`regex` returns the **first capture group**. A pattern with no capture group
returns nothing.

```json
{
  "domain.value": { "operator": "regex", "input": ["@fact:email.value", "[@](.+)$"] },
  "isInternal.value": { "operator": "=", "input": ["@fact:domain.value", "example.com"] }
}
```

With `email.value` of `"sam@example.com"`: `"example.com"` and `true`.

<Warning>
The pattern is written `"[@](.+)$"` rather than `"@(.+)$"` on purpose. A string
beginning with `@` is parsed as a fact reference before `regex` sees it, and the
rule silently produces nothing.
</Warning>

For initials and other joins with no separator, use `stringTemplate` rather than
`concat`, which always inserts a space:

```json
{
  "initials.value": {
    "operator": "stringTemplate",
    "input": [
      "{{1}}{{2}}",
      { "operator": "substring", "input": ["@fact:firstName.value", 0, 1] },
      { "operator": "substring", "input": ["@fact:lastName.value", 0, 1] }
    ]
  }
}
```

With `"Sam"` and `"Okonkwo"`: `"SO"`. `substring`'s third input is an **end
index**, not a length.

## Habits worth keeping

- **Name every intermediate step.** The engine works out the order, so splitting
  a calculation across several rules costs nothing and makes the output
  self-explaining when something is wrong.
- **Always write the default cell.** A ladder that matches nothing produces no
  fact, and a missing fact is indistinguishable from a broken one.
- **Check the operator name against the
  [reference](/advanced/rules/operations-reference) before debugging anything
  else.** An operator that does not exist produces no error.
- **Avoid dots in rule names** unless you are ready to write
  `$.rules_1['name.value']` downstream.
- **Do not reorder rules for speed.** Nothing short-circuits; every input is
  evaluated before the operator that uses it runs.
