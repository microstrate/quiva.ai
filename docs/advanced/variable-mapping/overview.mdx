# Variable Mapping

Every step in a flow is configured with a JSON object. Before the step runs, that object is resolved: **any string beginning with `$.` is read as a JSONPath expression** and replaced by the value it finds in the run's data. Everything else is copied through unchanged.

That resolver is variable mapping. It is the same code everywhere it appears, so what you learn here applies to every step, not just the [Map step](/flows/steps/map).

<Info>
The engine is [jsonpath-plus](https://github.com/JSONPath-Plus/JSONPath) behind a thin wrapper. The wrapper adds exactly one thing: `|` concatenation. There is no expression language, no transform functions and no filters beyond what JSONPath itself provides.
</Info>

---

## What is available to read

The run's data is a flat object with these keys:

| Key | Contents |
|---|---|
| `trigger` | The payload that started the run |
| `static` | The flow's Static Data block, itself resolved before the first step |
| `context` | Context variables supplied with the run |
| `env` | `auth_token`, `run_id`, and `headers` (a flat map of the request headers) |
| *step ID* | One key per **finished** step, holding that step's result |

A step's result is stored flat under its own ID. If a step's ID is `GET_ORDER`, its result is at `$.GET_ORDER`, and a field inside it at `$.GET_ORDER.data.total`. There is no `.output` or `.result` wrapper.

<Warning>
**Only finished steps are readable.** Branches that fan out from the same step run at the same time, so one of them cannot read another. A reference to a step that has not finished resolves to `[]`, not an error.
</Warning>

---

## Where mapping is applied

| Surface | What is resolved |
|---|---|
| Any step's payload | The whole payload object |
| Eval step | The **Params** object only — never the code |
| Flow **Static Data** | Resolved once, before the first step |
| Flow **Result** mapping | Resolved when the run finishes |
| Function and Flow step **Response Map** | Resolved against the step's result |
| Stream trigger `debounceOn` / `orderOn` | The key expression |

## The two forms

### A query

A string that starts with `$.` **and contains no `|`** is a JSONPath query. The value it finds is returned with its type intact.

```json
{ "name": "$.trigger.customer.name", "total": "$.GET_ORDER.data.total" }
```

```json
{ "name": "Dana Reyes", "total": 35 }
```

Numbers stay numbers, booleans stay booleans, objects and arrays keep their shape.

See [JSONPath](/advanced/variable-mapping/jsonpath) for everything a query can express.

### A concatenation

A string containing `|` is split on the `|` characters. Segments starting with `$.` are looked up and turned into text; every other segment is emitted literally; the pieces are joined.

```json
{ "summary": "Order |$.GET_ORDER.data.id| for |$.trigger.customer.name" }
```

```json
{ "summary": "Order ord_88 for Dana Reyes" }
```

The result is always a string. See [Concatenation](/advanced/variable-mapping/concatenation).

<Warning>
`|` is a delimiter, never an operator. `$.order.status|pending` does not fall back to `"pending"` — it produces `"shippedpending"`. There is no `| default(…)`, no `| upper`, and no chaining of any kind.
</Warning>

## Path shapes

The thing you write a mapping into does not have to be a string.

<Tabs>
  <Tab title="Object">
    Every value is resolved, to any depth. Keys are preserved.

    ```json
    { "customer": { "email": "$.trigger.email", "channel": "web" } }
    ```

    ```json
    { "customer": { "email": "dana@example.com", "channel": "web" } }
    ```
  </Tab>
  <Tab title="Array">
    Each element is resolved and the array keeps its length and order.

    ```json
    ["$.trigger.id", "static", 7]
    ```

    ```json
    ["T1", "static", 7]
    ```
  </Tab>
  <Tab title="A resolved key">
    A **key** may be an expression too. It is replaced by the value it resolves to.

    ```json
    { "$.trigger.email": { "total": "$.GET_ORDER.data.total" } }
    ```

    ```json
    { "dana@example.com": { "total": 35 } }
    ```

    Concatenation works in a key as well: `"user-|$.trigger.id"` becomes `"user-T1"`.
  </Tab>
  <Tab title="Anything else">
    Numbers, booleans and plain strings are copied through untouched. A string with no `$.` in it is literal text, even if it looks like a path.

    ```json
    { "message": "Order $.trigger.order_id is being processed" }
    ```

    ```json
    { "message": "Order $.trigger.order_id is being processed" }
    ```

    Interpolation needs `|`. Without it, nothing is substituted.
  </Tab>
</Tabs>

<Note>
A `null` in a mapping resolves to `{}`, not `null`. Omit the key instead.
</Note>

## The two failure modes

These are the only two ways a mapping surprises you, and both are silent.

### A path that matches nothing

**It resolves to `[]`, and the key stays in the output.**

```json
{ "userName": "$.node.name", "userPhone": "$.node.phone" }
```

against `{"node": {"name": "Alice"}}`:

```json
{ "userName": "Alice", "userPhone": [] }
```

The key is not removed, and the value is not `null` or `undefined`. A downstream step that checks for a missing key will not find one — test with `Array.isArray(x) && x.length === 0`, or add a trailing `|` to get `""` instead.

### A path that matches many where you expected one

**One hit returns the value itself. Zero or several hits return an array.** The shape of the result therefore depends on the data, not on the expression.

With three items priced 149.99, 150.00 and 9.99:

| Expression | Result |
|---|---|
| `$.items[?(@.price>100)].product` | `["Widget", "Gadget"]` |
| `$.items[?(@.price>149.99)].product` | `"Gadget"` |
| `$.items[?(@.price>9999)].product` | `[]` |

The same expression returns a list, a bare string, or an empty array purely according to how many rows matched. Anything reading that value must cope with all three, so prefer an [Eval step](/flows/steps/eval) when the count matters.

## Testing a mapping

The Map and Eval step editors each have a **Run Test** button that resolves the mapping against sample data using the same engine the flow uses, so what you see is what the step will produce.

<Note>
Editing a flow changes its **draft**. A change only affects the live flow once you **Publish** it.
</Note>
